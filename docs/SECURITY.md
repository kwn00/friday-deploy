# 보안 / 치팅 방지 설계

## 원칙

> **클라이언트는 적대적이라고 가정한다.**
> 브라우저에서 돌아가는 코드는 난독화하든 말든 사용자가 마음대로 읽고 고칠 수 있다.
> 따라서 "클라이언트를 못 고치게 막는 것"이 아니라 **"고쳐도 얻을 게 없게 만드는 것"** 이 목표다.

클라이언트의 역할은 두 가지뿐이다: **입력 의도 전송**, **서버가 준 상태 그리기**.

## 클라이언트가 보낼 수 있는 것 (전부)

| 메시지 | 필드 | 서버 검증 |
| --- | --- | --- |
| `hello` | 프로토콜 버전, 세션 토큰, 닉네임, 모드, (페어) 방 코드 | 토큰 HMAC·만료·1회용 검사, 닉네임 정제, 방 코드는 정확한 형식일 때만 |
| `input` | `seq`, `dx`, `dy` | 유한한 숫자, 각 축 ±1 이내, **서버에서 벡터 길이 1 이하로 재정규화**, `seq` 단조 증가 |
| `pick` | 선택지 **인덱스** | 서버가 제시한 선택지 안에 있을 때만 유효 |
| `start` | 없음 | 대기실의 방장이 보낸 것만 반영. 그 외에는 무시 |
| `pause` | 켜기/끄기 | 혼자 하는 방에서만 반영. 페어 방에서는 항상 거부 |
| `ping` | 타임스탬프 | 유한한 숫자 |

좌표·체력·경험치·처치 수·데미지·점수를 실어 보낼 수 있는 메시지는 **존재하지 않는다.**
알 수 없는 타입이나 형식이 틀린 메시지는 버려지고 위반으로 기록되며, 5회 누적 시 연결이 끊긴다.

## 위협별 대응

| 위협 | 대응 | 위치 |
| --- | --- | --- |
| 스피드핵 / 텔레포트 | 위치는 서버만 계산. 입력 벡터는 서버에서 정규화되어 최대 속도를 넘을 수 없음. 서버 틱 기준이라 클라이언트 시계 조작 무의미 | `shared/sim.ts` `setInput`, `step` |
| 무적 / 데미지·경험치 조작 | 해당 상태를 바꾸는 메시지 자체가 없음 | `shared/protocol.ts` |
| 원하는 업그레이드 고르기 | 선택지는 서버가 뽑고 인덱스만 받음. 제한 시간 초과 시 서버가 자동 선택 | `sim.ts` `pickOffer` |
| 난수 예측 (선택지·회복 아이템) | 레벨업 선택지와 회복 아이템 드롭은 운영체제 CSPRNG 에서 직접 뽑는 **비밀 난수**를 쓴다. 화면에 보이는 것(적 스폰 등)과 다른 난수라서 무엇을 관찰해도 예측할 수 없다. 두 난수가 소비되는 횟수는 서로의 결과에 영향을 받지 않게 했다(스폰이 어긋나는 것으로 비밀 결과가 새지 않게) | `sim.ts`, `server/world.ts` |
| 난수 예측 (스폰) | 적 스폰처럼 결과가 화면에 드러나는 것도 서버에서는 운영체제 CSPRNG 에서 직접 뽑는다. 출력에서 되짚어 갈 시드가 없어서, 스폰 위치를 아무리 모아도 다음 스폰을 계산할 수 없다. (예전의 31비트 시드는 처음 3초의 화면 정보로 약 2분 만에 찾을 수 있었고, 시드로 돌리는 sfc32 도 연속 출력 5개가 있으면 몇 초 만에 상태가 복원되는 것을 검토 중에 확인했다. 그래서 sfc32 는 테스트·도구에서만 쓴다) | `server/world.ts`, `shared/rng.ts` |
| 맵핵 (시야 밖 정보) | 플레이어별 관심 영역 반경 밖 엔티티는 스냅샷에 넣지 않음. 적 체력 등 불필요한 값도 미전송 (피격 이펙트를 위해 "이번 틱에 맞았는지" 1비트만 보낸다). 미니맵도 이 범위만 그린다. 예외: 같은 방 동료의 위치는 항상 보낸다 (협동 게임에서 숨길 정보가 아님) | `sim.ts` `buildSnapshot` |
| 점수 위조 | 리더보드 기록은 판이 끝날 때 서버가 직접 쓴다. 클라이언트가 점수를 제출하는 요청이 **존재하지 않는다** (`/api/leaderboard` 는 읽기 전용). 결과 메시지는 따로 HMAC 서명한다 | `room.ts` `finish`, `leaderboard.ts` |
| 순위표 도배 | 한 판에 기록 하나, 30초 미만은 제외, 기록을 세우려면 서버 시간으로 그만큼 실제로 버텨야 한다(빨리 감기 불가). 조회는 메모리에서 답하고 IP 당 제한 | `leaderboard.ts`, `index.ts` |
| 순위표 종류 속이기 | 판이 진행되는 동안 한 번이라도 2명 이상이 있었으면 함께 순위표로만 간다 (도움을 받은 판이 혼자 순위표에 오르지 않는다). 대기실에만 있다 나간 접속은 세지 않는다 (혼자 한 판이 함께 순위표로 가지 않는다). 이름은 처음부터 끝까지 있던 사람만 오른다 | `room.ts` `report` |
| 남의 기록에 이름 올리기 | 함께 한 판에는 처음부터 끝까지 있던 사람만 오른다. 도중에 들어온 사람과 관전자는 제외 | `room.ts` `report` |
| DB 를 통한 공격 / 장애 전파 | 파라미터 쿼리만 사용. 순위는 메모리에서 계산하고 저장은 뒤에서 재시도하므로, DB 가 느리거나 죽어도 게임 루프와 순위 조회는 영향을 받지 않는다 | `leaderboard.ts`, `store-postgres.ts` |
| 세션 위조 / 탈취 재사용 | 서버 발급 HMAC 토큰, 10분 만료, **1회용**, `timingSafeEqual` 비교. 토큰은 URL 이 아닌 첫 메시지로 전달(로그 노출 방지) | `server/security.ts` |
| Cross-Site WebSocket Hijacking | 업그레이드 시 `Origin` 검사 (same-origin + 허용 목록) | `security.ts` `originAllowed` |
| 메시지 폭주 / DoS | 연결별 토큰 버킷(초당 40), 프레임 512B 제한, 클라이언트의 바이너리 프레임 거부, IP 당 연결 6개, 전체 연결·방 개수 상한, hello 5초 타임아웃, 하트비트, 방치 방·대기실 정리, 느린 클라이언트 스냅샷 드롭, 정적 파일 요청도 IP 당 제한 | `server/index.ts`, `room.ts` |
| 압축을 이용한 CPU 고갈 | WebSocket 압축(permessage-deflate)은 **기본으로 끈다**. 켜면 모든 프레임이 zlib 을 거쳐, 0.1 CPU 서버에서는 평범한 접속 36개로 전원이 끊기는 것이 측정으로 확인됐다(끄면 72개에서도 지연만 증가). 전송량은 스냅샷 이진 인코딩으로 줄인다 | `server/index.ts`, `shared/codec.ts` |
| IP 위조로 IP 당 제한 우회 | `X-Forwarded-For` 맨 앞 값은 클라이언트가 넣을 수 있으므로 쓰지 않는다. 엣지가 덮어쓰는 단일 값 헤더(`CLIENT_IP_HEADER`, Render 는 `cf-connecting-ip`) 또는 오른쪽에서 신뢰 홉 수만큼의 값(`TRUST_PROXY=n`)만 쓰고, 값이 IP 가 아니면 소켓 주소로 떨어진다(제한이 더 엄격해지는 쪽). IPv6 는 /64 단위로 묶는다 | `security.ts` `resolveClientIp` |
| 남의 페어 방에 무단 입장 | 방 코드는 서버 CSPRNG 로 만든 6자리(32종 문자, 약 10억 가지). 틀린 코드도 1회용 세션 토큰을 소모하므로 대입은 세션 발급 제한(IP 당 초당 0.5개)에 묶인다. 방은 4명까지 | `room.ts` `RoomManager`, `index.ts` |
| 일시정지 악용 | 일시정지는 혼자 하는 방에서만 받아들이고 한 번에 최대 10분, 한 판에 합쳐서 30분 (껐다 켜기를 반복해 방을 끝없이 붙잡아 둘 수 없다). 멈춘 동안에는 시뮬레이션도 전송도 하지 않는다. 페어 방에서는 누가 보내든 거부한다 (한 사람이 다른 사람의 게임을 멈추거나 그 틈에 쉴 수 없다) | `room.ts` `onPause` |
| 쓰러진 뒤 다시 들어와 부활 | 페어 판에서 누군가 쓰러진 뒤에 들어오는 사람은 다음 판까지 관전한다. 나갔다 다시 들어오기를 반복해 판을 끝없이 이어갈 수 없다 | `room.ts` `join` |
| 남의 기록에 무임승차 | 도중에 합류한 사람의 결과에는 판 전체 시간이 아니라 본인이 함께 한 시간만 서명한다 | `room.ts` `finish` |
| 요청 하나로 서버 전체 다운 | 형식이 틀린 요청 대상(`//`, `/\` 등)에서 URL 파서가 던지는 예외로 프로세스가 죽던 문제를 고쳤다(400/404 응답). HTTP·업그레이드·메시지·방 틱 처리 전부를 예외로부터 보호해, 한 요청이나 한 방의 오류가 다른 방을 끝내지 않는다 | `security.ts` `pathnameOf`, `index.ts`, `room.ts` |
| 끊긴 뒤에도 남아 있는 연결 | 서버가 끊기로 한 연결의 메시지는 더 처리하지 않고, close 에 응답하지 않으면 1초 뒤 강제로 닫는다 | `index.ts` `drop` |
| 대기실 가로채기 / 붙잡아 두기 | 게임 시작은 방장(가장 먼저 들어온 사람)만 가능. 방장이 나가면 다음 사람이 이어받는다. 시작하지 않은 대기실은 10분 뒤 닫히며, 입력을 보내도 연장되지 않는다 | `room.ts` `onStart`, `tick` |
| 리플레이 / 순서 조작 | `seq` 가 증가하지 않는 입력은 위반 처리 | `room.ts` `onInput` |
| XSS (닉네임 등) | 서버에서 닉네임을 문자/숫자/일부 기호로 정제 + 클라이언트는 `textContent`/캔버스만 사용 (`innerHTML` 미사용) + CSP `script-src 'self'` | `protocol.ts` `sanitizeName`, `client/main.ts` |
| 클릭재킹 / MIME 스니핑 | `frame-ancestors 'none'`, `X-Frame-Options`, `nosniff` 등 보안 헤더 | `security.ts` |
| 경로 탈출 (정적 파일) | 정규화 후 배포 디렉터리 내부인지 확인 | `server/index.ts` `serveStatic` |
| 시크릿 누락 배포 | 프로덕션에서 `SESSION_SECRET` 미설정 시 기동 거부 | `security.ts` |

## 검증된 것

`npm test` 가 조작된 메시지 거부, 속도 상한, 미제시 업그레이드 선택 불가, 방 코드·일시정지 메시지 검증, IP 판별,
이진 스냅샷의 왕복 정확도와 손상된 데이터 처리를 확인한다.
또한 실제 서버를 대상으로 다음 시도가 모두 차단됨을 확인했다:
다른 Origin 접속(403), 위조 토큰(4003), 토큰 재사용(4003), `dx: 50` 스피드핵(무시), 상태 덮어쓰기 필드(무시), 임의 `pick`(위반), 메시지 500개 폭주(1008), 5KB 프레임(1009), hello 없이 대기(4001),
페어 방에서 손님이 보낸 시작(무시), 페어 방에서 누가 보내든 일시정지(거부, 월드 계속 진행), 틀린 방 코드(4005 + 토큰 소모), 정원 초과 입장(4005), 형식이 틀린 방 코드·일시정지(위반), 이전 버전 클라이언트(4002), 클라이언트의 바이너리 프레임(1003), 위조한 `X-Forwarded-For` 로 IP 당 제한 우회(실패), 같은 주소의 정적 파일 반복 요청(429),
서버를 죽이던 요청 대상 `//`, `/\`, `//?a=1`, `http://a:b/` 등(400 또는 404, 서버 유지).

## 알려진 한계 / 다음 단계

서버 권위 구조로도 막을 수 없는 것들이며, 멀티플레이 확장 시 순서대로 다룬다.

- **자동 조작 봇**: 정상 입력을 기계가 대신 넣는 것은 프로토콜 수준에서 구분 불가 → 입력 패턴 통계, 리플레이 저장 후 사후 검증, 신고 시스템
- **다중 계정 / 어뷰징**: 현재 익명 세션 → 계정 연동(OAuth), 계정 단위 레이트리밋
- **첫 선택지가 마음에 들 때까지 다시 시작하기**: 선택지를 예측하거나 바꿀 수는 없지만, 판을 버리고 새로 시작하는 것은 막지 않는다 (버린 판은 기록되지 않으므로 드는 것은 시간뿐)
- **한 사람이 두 접속으로 함께 순위표에 오르기**: 계정이 없어서 두 접속이 같은 사람인지 알 수 없다. 방 코드를 아는 접속만 들어올 수 있고, 판이 시작된 뒤에 두 명이 있었던 판만 함께 순위표로 간다
- **솔로 일시정지와 기록**: 일시정지는 생각할 시간을 준다. 멈춰 있던 시간은 생존 시간에 들어가지 않고 기록에 따로 남기지만(`pausedSeconds`), 순위표에서 구분해 보여주지는 않는다
- **익명 닉네임**: 계정이 없어서 누구나 아무 닉네임이나 쓸 수 있고(사칭 가능), 부적절한 이름을 걸러내지 않는다. 지우려면 DB 에서 직접 지워야 한다 → 계정 연동이 다음 단계
- **자동 조작 봇의 기록**: 정상 입력을 기계가 넣은 판도 규칙상 정상이므로 순위표에 오른다
- **끊긴 연결**: 재접속이 없어서 연결이 끊기면 그 판은 끝난다 (모바일에서 앱을 오래 떠나면 브라우저가 연결을 끊는다)
- **L7 DDoS**: 앱 내부 제한만 있음 → 배포 시 CDN/WAF. 프록시 뒤에서는 `CLIENT_IP_HEADER` / `TRUST_PROXY` 를 그 프록시에 맞게 설정
- **IP 헤더 신뢰의 전제**: `cf-connecting-ip` 는 요청이 Cloudflare 를 거쳐 올 때만 믿을 수 있다. Render 원본에 Cloudflare 를 우회해 직접 닿는 경로가 있다면 위조 가능하다(확인 못 함). IP 당 제한은 남용 완화용이고 치팅 방지의 근거가 아니다
- **호스팅 전송량 소진**: 무료 호스트의 월 전송량을 일부러 태워 서비스를 멈추게 할 수 있다. IP 당 연결·요청 제한과 작은 스냅샷은 그 속도를 늦출 뿐 막지는 못한다(주소 여러 개면 그만큼 빨라진다). 막으려면 앞단의 CDN/WAF 가 필요하고, 그 전까지는 대시보드에서 사용량을 지켜봐야 한다
- **약한 서버의 CPU**: 0.1 CPU 급에서는 압축을 끈 상태에서도 접속 수십 개면 스냅샷이 초당 12~16개로 떨어진다(측정). 전원 끊김은 아니지만 느려진다
- **전송 구간**: 반드시 HTTPS/WSS(TLS) 뒤에서 서비스할 것
