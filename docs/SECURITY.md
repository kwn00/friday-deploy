# 보안 / 치팅 방지 설계

## 원칙

> **클라이언트는 적대적이라고 가정한다.**
> 브라우저에서 돌아가는 코드는 난독화하든 말든 사용자가 마음대로 읽고 고칠 수 있다.
> 따라서 "클라이언트를 못 고치게 막는 것"이 아니라 **"고쳐도 얻을 게 없게 만드는 것"** 이 목표다.

클라이언트의 역할은 두 가지뿐이다: **입력 의도 전송**, **서버가 준 상태 그리기**.

## 클라이언트가 보낼 수 있는 것 (전부)

| 메시지 | 필드 | 서버 검증 |
| --- | --- | --- |
| `hello` | 프로토콜 버전, 세션 토큰, 닉네임, 모드, (페어) 방 코드 | 토큰 HMAC·만료·1회용 검사, 닉네임 정제, 방 코드는 정확한 형식일 때만 |
| `input` | `seq`, `dx`, `dy` | 유한한 숫자, 각 축 ±1 이내, **서버에서 벡터 길이 1 이하로 재정규화**, `seq` 단조 증가 |
| `pick` | 선택지 **인덱스** | 서버가 제시한 선택지 안에 있을 때만 유효 |
| `start` | 없음 | 대기실의 방장이 보낸 것만 반영. 그 외에는 무시 |
| `pause` | 켜기/끄기 | 혼자 하는 방에서만 반영. 페어 방에서는 항상 거부 |
| `ping` | 타임스탬프 | 유한한 숫자 |
| `resume` | 프로토콜 버전, 세션 토큰, 이어받기 열쇠 | 토큰은 `hello` 와 같은 검사(1회용). 열쇠는 정확한 형식일 때만 받고, 서버가 지키고 있는 자리의 열쇠와 `timingSafeEqual` 로 비교한다. **상태를 실어 보낼 필드가 없다**: 어느 자리인지 가리킬 뿐이고, 돌려받는 것은 서버에 있던 상태 그대로다 |
| `leave` | 없음 | 보낸 연결 자신의 자리만 비운다 |

좌표·체력·경험치·처치 수·데미지·점수를 실어 보낼 수 있는 메시지는 **존재하지 않는다.**
알 수 없는 타입이나 형식이 틀린 메시지는 버려지고 위반으로 기록되며, 5회 누적 시 연결이 끊긴다.

## 위협별 대응

| 위협 | 대응 | 위치 |
| --- | --- | --- |
| 스피드핵 / 텔레포트 | 위치는 서버만 계산. 입력 벡터는 서버에서 정규화되어 최대 속도를 넘을 수 없음. 서버 틱 기준이라 클라이언트 시계 조작 무의미 | `shared/sim.ts` `setInput`, `step` |
| 내 캐릭터를 앞서 그리기 (클라이언트 예측) | 화면은 내 캐릭터만 서버의 답을 기다리지 않고 입력대로 먼저 그린다. 그 위치는 **서버로 보내지 않고, 서버는 받는 통로도 없다**: 위치·피격·획득은 여전히 서버 위치로만 판정한다. 예측을 조작해도 달라지는 것은 자기 화면뿐이다. 이를 위해 스냅샷에 실리는 값(마지막으로 받은 내 입력 번호, 그 입력으로 움직인 틱 수, 틱 사이의 도착 위치)은 받는 사람 자신의 것뿐이고 서버가 잰 것이다. 서버는 입력을 틱 중간의 도착한 때부터 적용하는데, 그 때는 서버 시계로 재고(클라이언트가 보내지 않는다) 앞뒤 입력 모두 길이 1 이하라서 한 틱에 가는 거리는 늘지 않는다 | `client/predict.ts`, `room.ts` `onInput`, `sim.ts` `setInput` |
| 무적 / 데미지·경험치 조작 | 해당 상태를 바꾸는 메시지 자체가 없음 | `shared/protocol.ts` |
| 원하는 업그레이드 고르기 | 선택지는 서버가 뽑고 인덱스만 받음. 칸(무기 6 · 패시브 6)과 단계 상한도 서버가 지킨다: 가진 칸이 다 차면 새 것은 선택지에 나오지 않고, 최대 단계인 것도 나오지 않는다. 선택지가 4개가 되는 행운(배포 기도), 가진 것을 먼저 넣는 굴림, rarity 무게로 뽑기도 모두 비밀 난수로 정한다. 제한 시간 초과 시 서버가 자동 선택 | `sim.ts` `pickOffer`, `checkLevelUp` |
| 보물상자 내용 조작·예측 | 상자는 보스가 쓰러질 때 서버가 놓고, 닿았는지도 서버가 위치로 판정한다. 몇 개가 들었는지(1/3/5)와 무엇이 오르는지는 비밀 난수로 정하고, 연 사람에게 결과만 알린다. 상자를 달라거나 열었다고 말하는 메시지는 없다. 보스마다 정해진 기본 개수보다 적게 나오지 않는다 (예전에는 운이 좋을수록 8분 상자가 오히려 줄었다). 굴리는 순서와 비밀 난수를 쓰는 횟수는 예전과 같다 | `sim.ts` `openChest`, `combat.ts` `dropChest` |
| 진화 조작 (조건 없이 진화, 진화한 무기를 선택지로 받기) | 진화할지는 서버가 상자를 열 때 서버의 강화 단계로만 정한다 (재료 무기 최대 단계 + 짝 패시브). 진화를 요청하는 메시지는 **없다**. 진화한 무기와 진화해서 없어진 재료 무기는 서버가 선택지에서 뺀다. 클라이언트의 짝 안내와 "상자를 열면 진화" 표시는 서버가 보낸 내 강화 단계로 그리기만 한다 | `content.ts` `readyEvolutions`, `sim.ts` `openChest`·`checkLevelUp` |
| 난수 예측 (선택지·회복 아이템·상자) | 레벨업 선택지, 보물상자 내용, 회복 아이템 드롭은 운영체제 CSPRNG 에서 직접 뽑는 **비밀 난수**를 쓴다. 화면에 보이는 것(적 스폰 등)과 다른 난수라서 무엇을 관찰해도 예측할 수 없다. 비밀 난수의 결과가 보이는 난수를 뽑는 횟수를 바꾸지 않게 했다(스폰이 어긋나는 것으로 비밀 결과가 새지 않게). 예외는 플레이어가 받은 강화(선택지·상자)가 무기를 바꾸는 경우뿐이고, 그것은 화면에 그대로 드러나는 결과다 | `sim.ts`, `server/world.ts` |
| 난수 예측 (스폰) | 적 스폰처럼 결과가 화면에 드러나는 것도 서버에서는 운영체제 CSPRNG 에서 직접 뽑는다. 출력에서 되짚어 갈 시드가 없어서, 스폰 위치를 아무리 모아도 다음 스폰을 계산할 수 없다. (예전의 31비트 시드는 처음 3초의 화면 정보로 약 2분 만에 찾을 수 있었고, 시드로 돌리는 sfc32 도 연속 출력 5개가 있으면 몇 초 만에 상태가 복원되는 것을 검토 중에 확인했다. 그래서 sfc32 는 테스트·도구에서만 쓴다) | `server/world.ts`, `shared/rng.ts` |
| 맵핵 (시야 밖 정보) | 플레이어별 관심 영역 반경 밖 엔티티는 스냅샷에 넣지 않음. 적 체력 등 불필요한 값도 미전송 (피격 이펙트를 위해 "이번 틱에 맞았는지" 1비트만 보낸다). 예외: 보스는 머리 위 체력바를 위해 남은 체력의 비율(1~100, 올림)만 보낸다 (체력 자체는 보내지 않는다. 0.2.2). 미니맵도 이 범위만 그린다. 예외: 같은 방 동료의 위치는 항상 보낸다 (협동 게임에서 숨길 정보가 아님) | `sim.ts` `buildSnapshot` |
| 무기 효과로 정보 얻기 | 무기의 조준·폭발·얼림 판정은 모두 서버가 한다. 화면에 보내는 것은 시야 안의 투사체·소환물 위치와, 시야 안에 새로 생긴 바닥 영역(생길 때 한 번만, 남는 시간과 함께)뿐이다. 소환물(카나리아·부엉이, 24시간 모니터링의 두 마리)과 러버덕은 주인 기준 위치라 숨길 정보가 아니다 | `sim.ts` `buildSnapshot` |
| 많은 무기·적으로 서버·전송량 부담 늘리기 | 적은 한 방에 300마리(보스·이벤트를 합쳐 500마리)까지만, 사람이 늘어도 같은 상한이다. 투사체는 한 방에 최대 320개, 피해를 주는 바닥 영역은 200개, 번쩍이기만 하는 효과는 따로 200개까지만 만든다. 일반 적과 경험치는 화면 바로 바깥(304px)까지만 보낸다 (먼 적의 위치도 덜 드러난다). 적은 틱마다 공간 격자에 넣어 충돌 계산을 줄였다 (4명이 모두 최대 장비일 때 스냅샷까지 합친 틱 평균 0.43~0.61ms, 측정). 바닥 영역은 생길 때 한 번만 보낸다. 한 사람 전송량은 처음 15분에 9~31MB 로 0.1.1 보다 대체로 적다 (측정) | `combat.ts`, `constants.ts` |
| 필드 아이템 예측·조작 | 언제, 어디에, 무엇이 놓일지는 서버가 비밀 난수(운영체제 CSPRNG)로 정한다. 보이는 난수를 쓰지 않으므로 적 스폰을 관찰해도 알 수 없고, 아이템이 놓여도 스폰의 흐름이 달라지지 않는다. 클라이언트는 아이템을 달라거나 주웠다고 말하는 메시지를 보낼 수 없다: 서버가 위치로 판정한다. 필드 아이템의 위치는 일부러 모두에게 보낸다 (미니맵으로 찾아가는 것이 놀이의 일부이고, 모든 플레이어가 똑같이 받는다) | `sim.ts` `spawnFieldItem`, `step`, `buildSnapshot` |
| 부활 조작 | 가진 백업 수와 되살아나는 판정은 서버에만 있다. 하나만 가질 수 있고, 쓰러질 순간에 서버가 써서 되살린다. 무적 시간도 서버가 센다. 클라이언트에는 화면 표시용으로 내 백업 수와 "무적 중" 표시만 간다 | `sim.ts` `revive`, `canTake` |
| 점수 위조 | 리더보드 기록은 판이 끝날 때 서버가 직접 쓴다. 클라이언트가 점수를 제출하는 요청이 **존재하지 않는다** (`/api/leaderboard` 는 읽기 전용). 결과 메시지는 따로 HMAC 서명한다 | `room.ts` `finish`, `leaderboard.ts` |
| 순위표 도배 | 한 판에 기록 하나, 30초 미만은 제외, 기록을 세우려면 서버 시간으로 그만큼 실제로 버텨야 한다(빨리 감기 불가). 조회는 메모리에서 답하고 IP 당 제한 | `leaderboard.ts`, `index.ts` |
| 30분 뒤 끝없이 버티기 (기록 늘리기) | 30분 뒤에는 판 길이에 상한이 없고 순위는 버틴 시간이 먼저다. 그래서 월요일 아침(사신)을 멈출 수 있으면 기록이 늘어난다: 예전에는 코드 프리즈로 사신을 얼려 몇 분씩 더 버틸 수 있었다 (측정: 코드 프리즈 7단계로 1~6분, 부활까지 더하면 10분 넘게). 지금 사신은 얼지 않고(빙결 저항 1.1, 방화벽의 약화를 받지 않아 내려가지 않는다), 디버거에 멈추지 않고(보스), git clean 에 지워지지 않고, 넉백에 밀리지도 늦춰지지도 않는다 (끌려오는 것은 걷는 것보다 느려지지 않는다). 남는 것은 부활(스냅샷·백업)과 2단계 인증의 방패뿐이라, 30분 뒤 혼자는 몇 초~십몇 초, 4명이 저마다 부활을 모두 가져도 1분 안쪽에 끝난다 (측정) | `content.ts` `monday`, `combat.ts` `hit`·코드 프리즈, `sim.ts` 적 이동 |
| 순위표 종류 속이기 | 판이 진행되는 동안 한 번이라도 2명 이상이 있었으면 함께 순위표로만 간다 (도움을 받은 판이 혼자 순위표에 오르지 않는다). 대기실에만 있다 나간 접속은 세지 않는다 (혼자 한 판이 함께 순위표로 가지 않는다). 이름은 처음부터 끝까지 있던 사람만 오른다 | `room.ts` `report` |
| 남의 기록에 이름 올리기 | 함께 한 판에는 처음부터 끝까지 있던 사람만 오른다. 도중에 들어온 사람은 제외하고, 캐릭터 없이 관전으로 들어온 사람은 판이 시작된 직후에 들어왔더라도 제외한다 (한 번도 플레이하지 않았다). 이름 옆의 기여도(개인 처치 수)와 사람별 아이템(무기·패시브와 단계)도 서버가 가진 값이다. 저장할 때와 DB·응답에서 읽을 때 아는 아이템·단계·칸 수만 남긴다 | `room.ts` `report`, `leaderboard.ts` `record` |
| 아이템 통계 위조 · 쏠리게 하기 | 통계의 숫자(선택지에 나온 횟수, 고른 횟수, 시간 초과 자동 선택, 보물상자, 끝날 때 가진 것)는 모두 서버의 시뮬레이션이 센다. 클라이언트가 보내는 것은 기존과 같이 선택지 **인덱스**뿐이고, 통계를 보내는 통로는 **없다** (`/api/stats/upgrades` 는 읽기 전용). 리더보드와 같은 판(30초 이상, 처음부터 함께 한 사람)만 세므로 판을 반복해 숫자를 쏠리게 하려면 서버 시간으로 실제로 버텨야 하고, 판 수는 세션 발급·연결 수 제한에 묶인다. 같은 판은 두 번 세지 않고, 저장소에 더하는 묶음마다 id 를 남겨 다시 보낸 묶음을 두 번 더하지 않는다. 합계만 저장하고 이름·IP 는 저장하지 않는다 | `sim.ts` `tally`, `stats.ts`, `room.ts` `report` |

## 알려진 한계 / 다음 단계

서버 권위 구조로도 막을 수 없는 것들이며, 멀티플레이 확장 시 순서대로 다룬다.

- **자동 조작 봇**: 정상 입력을 기계가 대신 넣는 것은 프로토콜 수준에서 구분 불가 → 입력 패턴 통계, 리플레이 저장 후 사후 검증, 신고 시스템
- **다중 계정 / 어뷰징**: 현재 익명 세션 → 계정 연동(OAuth), 계정 단위 레이트리밋
- **첫 선택지가 마음에 들 때까지 다시 시작하기**: 선택지를 예측하거나 바꿀 수는 없지만, 판을 버리고 새로 시작하는 것은 막지 않는다 (버린 판은 기록되지 않으므로 드는 것은 시간뿐)
- **한 사람이 두 접속으로 함께 순위표에 오르기**: 계정이 없어서 두 접속이 같은 사람인지 알 수 없다. 방 코드를 아는 접속만 들어올 수 있고, 판이 시작된 뒤에 두 명이 있었던 판만 함께 순위표로 간다
- **솔로 일시정지와 기록**: 일시정지는 생각할 시간을 준다. 멈춰 있던 시간은 생존 시간에 들어가지 않고 기록에 따로 남기지만(`pausedSeconds`, 실제로 멈춰 있던 시간이다: 예산에서 뺀 최소 3초가 아니다), 순위표에서 구분해 보여주지는 않는다
- **익명 닉네임**: 계정이 없어서 누구나 아무 닉네임이나 쓸 수 있고(사칭 가능), 부적절한 이름을 걸러내지 않는다. 지우려면 DB 에서 직접 지워야 한다 → 계정 연동이 다음 단계
- **자동 조작 봇의 기록**: 정상 입력을 기계가 넣은 판도 규칙상 정상이므로 순위표에 오른다
- **서버가 새로 시작되면 이어갈 수 없다**: 방과 자리는 프로세스 메모리에 있다. 배포하거나 호스트가 인스턴스를 재시작하면 하던 판은 끝난다
- **연결이 끊긴 채 탭을 닫은 사람**: 나갔다고 알릴 방법이 없어서 자리가 시간이 될 때까지 남는다 (페어 판에서는 캐릭터가 최대 2분 서 있고, 혼자 하는 판은 최대 10분 멈춘 채 남는다). 주소당 지켜 두는 자리 수 제한이 그 수를 묶는다
- **이어받기 열쇠는 브라우저의 탭 저장소(sessionStorage)에 있다**: 새로고침 뒤에도 이어지게 하기 위해서다. 같은 기기를 쓰는 사람이나 XSS 가 읽을 수 있지만, 얻는 것은 그 판의 그 자리 하나뿐이고(계정·기록과 무관) 자리가 비워지면 쓸모없다. XSS 는 CSP 와 `textContent` 로 막는다. 탭 저장소에는 아직 참가하지 않은 초대 방 코드(`invite`)도 남는다: 주소(`?room=`)에 있던 것과 같은 값이고 방에 들어가면 지운다. 방 코드는 비밀이 아니고, 들어가려면 서버가 확인한다
- **테마는 브라우저 시계로 고른다**: 보이는 것(색·눈·장식)만 바뀌고 판정·기록·통신과는 무관하다. 시계를 바꿔도 자기 화면의 테마만 달라진다
- **같은 주소를 쓰는 여러 사람**: 주소당 한도(연결 6, 지켜 둔 자리 6)는 공유기나 통신사 NAT 를 함께 쓰는 사람들이 나눠 쓴다. 넘치면 가장 오래 끊겨 있던 자리부터 비워진다
- **L7 DDoS**: 앱 내부 제한만 있음 → 배포 시 CDN/WAF. 프록시 뒤에서는 `CLIENT_IP_HEADER` / `TRUST_PROXY` 를 그 프록시에 맞게 설정
- **IP 헤더 신뢰의 전제**: `cf-connecting-ip` 는 요청이 Cloudflare 를 거쳐 올 때만 믿을 수 있다. Render 원본에 Cloudflare 를 우회해 직접 닿는 경로가 있다면 위조 가능하다(확인 못 함). IP 당 제한은 남용 완화용이고 치팅 방지의 근거가 아니다
- **호스팅 전송량 소진**: 무료 호스트의 월 전송량을 일부러 태워 서비스를 멈추게 할 수 있다. IP 당 연결·요청 제한과 작은 스냅샷은 그 속도를 늦출 뿐 막지는 못한다(주소 여러 개면 그만큼 빨라진다). 막으려면 앞단의 CDN/WAF 가 필요하고, 그 전까지는 대시보드에서 사용량을 지켜봐야 한다
- **약한 서버의 CPU**: 0.1 CPU 급에서는 압축을 끈 상태에서도 접속 수십 개면 스냅샷이 초당 12~16개로 떨어진다(측정). 전원 끊김은 아니지만 느려진다
- **전송 구간**: 반드시 HTTPS/WSS(TLS) 뒤에서 서비스할 것
- **수평 확장**: 세션 1회용 기록과 방 상태가 프로세스 메모리에 있음 → 다중 인스턴스 시 Redis 등 공유 저장소와 방 단위 스티키 라우팅 필요
